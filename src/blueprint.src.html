Template · Power Platform target architecture

Power Platform Enterprise Blueprint

A reference architecture for running Power Apps, Power Automate and Copilot Studio in a global organisation. It covers how environments are laid out, how data policies stack, how capacity is paid for and charged back, and how the platform reports on itself. Each sheet shows a diagram first, then the detail behind it. Sheet 10 works through common governance scenarios, such as cross-charging and restricting the GitHub Copilot harness. Sheet 11 covers the operating loop: control, monitor, report and cross-charge.

Act now

No new AI Builder credits from 1 November 2026

From that date, AI Builder capacity add-ons reach end of life and new or renewed premium licences no longer include seeded AI Builder credits. Credits you already hold are honoured to the end of your contract term. After that, AI Builder features keep working but draw Copilot Credits, and fail if none are available. Inventory AI Builder use now, plan Copilot Credits for the affected environments, and turn off auto-renew of AI Builder add-ons. Sheet 05 has the detail.

Plan now

Managed environments need premium licences, enforced from February 2027

Every user who runs an app or cloud flow in a managed environment needs a premium licence (Power Apps Premium, Power Automate Premium or a qualifying Dynamics 365 licence) or a pay-as-you-go meter. Microsoft has shown in-app warnings since June 2026. From February 2027, unlicensed users can't open apps in managed environments. This blueprint makes most environments managed (D4), so run the Users requiring licenses in Managed Environments report and budget for the result before you scale out.

Decisions

Ten decisions this blueprint makes

D1 · TENANT SHAPE

One global tenant. Environment groups are cut by tier × region to mirror the operating regions.

D2 · DEFAULT ENV

The default environment becomes Personal Productivity: core Microsoft 365 and non-blockable connectors only, routing on, Share with Everyone off.

D3 · DATA ZONES

Three zones: G personal, A business, R restricted, each mapped 1:1 to environment groups. Allowlisting starts in Zone R.

D4 · MANAGED

Every environment except the default and Teams environments is managed, so group rules hold the settings. The trade-off: their users need premium licences, enforced from Feb 2027.

D5 · RELEASE

Production accepts managed solutions only, deployed by Pipelines as a service principal. Zone R uses pro-dev CI/CD.

D6 · PAYING

A prepaid baseline is pooled and allocated per environment. Growth runs on pay-as-you-go through one billing policy per region × cost owner.

D7 · AI CREDITS

No new AI Builder credits after 1 Nov 2026; existing ones run to contract end. Plan Copilot Credits for every AI Builder use.

D8 · TELEMETRY

Native inventory and data export feed a Fabric governance lakehouse. The CoE Starter Kit is not the base for new build.

D9 · AGENTS

Agents are identities: new ones get an Entra Agent ID. Add quarterly access reviews and zone-specific connector rules.

D10 · PEOPLE

A global Platform CoE, regional hubs and BU champions. Three maker tiers with promotion triggers read from inventory.

Assumptions to confirm

One Microsoft Entra tenant for all regions; tenant home geo in Europe; Microsoft 365 E3/E5 as the user baseline; sovereign-cloud jurisdictions (for example mainland China) handled separately, outside this design. Environment names and examples are illustrative.

Sheet 01 · Architecture

Reference architecture

Five layers. People configure a tenant-wide control plane, which enforces policy on environments grouped into zones. Environments reach data through a few governed paths, and every layer emits telemetry that returns to the people who run the platform.

Products on this sheet
Power PlatformPower AppsPower AutomateCopilot StudioDataverse

Why five layers

Each layer has one owner and one change process. The control plane changes through the CoE change board; zones change through group rule templates; integration paths change through Security. That keeps a change in one place from silently weakening another.

Where agents fit

Copilot Studio agents live in Zone A for read-only assistants and in Zone R as soon as they take actions on business systems. Their tools (connectors and MCP servers) are governed by the same data policies as apps and flows, and each agent has its own Entra identity.

Creation & clean-up

  • Creation is restricted. Only admins create production, sandbox and trial environments. Developer environments come only through routing; everything else goes through an intake form.
  • Licence auto-claim is on. A user who opens a premium or managed-environment app gets a Power Apps licence, if one is free in the pool. Keep headroom in the pool, because unlicensed users are blocked in managed environments from February 2027.
  • The default environment gets cleaned out. Shared multi-maker assets move to shared dev, then production. Single-maker assets move to the owner's dev environment. Anything unused for 90 days goes to quarantine after the owner is told.

Sheet 03 · Data loss prevention

Data policy layering

Status check

Microsoft Learn documents ACP as generally available per workload once design-time enforcement reaches that maker portal (Power Automate, then Copilot Studio, then Power Apps). Until then it is enforced at runtime only for that workload. Start in mixed mode (the default). Don't switch Zone R to ACP-only while custom, HTTP, desktop-flow and Copilot Studio virtual-connector controls still live in the classic layer 2 policy. Endpoint filtering is still in preview and doesn't evaluate values held in environment variables.

Sheet 04 · Application lifecycle

Release paths

Two paths share one rule: nothing unmanaged reaches production. Citizen and fusion teams use Pipelines in Power Platform from a host in their own geo. Zone R and Tier 3 solutions use a pro-dev path that builds the managed artifact from source and runs automated tests.

Products on this sheet
PipelinesPower AppsPower AutomateDataverse

Solution standards

  • Turn on Create new canvas apps and cloud flows in Dataverse solutions in every dev environment, and have each maker set a preferred solution, so new assets land in a solution.
  • Every endpoint, site URL and ID goes in an environment variable. Every connection goes through a connection reference owned by a service account, never a person. Endpoint filtering doesn't evaluate values held in environment variables, so for those endpoints the API gateway is the real control.
  • The solution checker is enforced by group rule: Block in every target (Block stops imports with critical issues only). Review high findings in the pull request for Zone R.

Source & identity

  • Dataverse Git integration (Azure DevOps, or GitHub in preview; requires managed environments) is on for shared dev and every Tier 2 or Tier 3 solution, so any version can be rebuilt.
  • One deployment service principal per geo, owned in Entra by the Platform CoE, with Deployment Pipeline Administrator in the pipelines host and System Administrator in target environments.
  • Pipelines targets must be managed environments. From October 2026, Pipelines warns admins about unmanaged targets and blocks deployments to them after 30 days.
  • Approvals run as a flow in the Pipelines host, so every gate leaves an audit trail.

Sheet 05 · Credit consumption & FinOps

Paying for capacity

Capacity reaches environments by two routes. The prepaid route pools licences and capacity packs at tenant level and allocates them per environment. The metered route links environments through a billing policy to an Azure subscription. Both end in a chargeback to the region that owns the P&L.

Products on this sheet
Copilot CreditsAI BuilderDataverse
Pay-as-you-go caveat

Linking an environment to a billing policy changes what it can use: Process licences, the unattended RPA add-on, app passes and Power Pages capacity are ignored there. Keep RPA and app-pass workloads in environments without a billing policy.

How do we charge each business unit for the Power Platform and Copilot Studio capacity it actually uses?

Steps

  1. Register a cost owner for every environment: environment ID, region, BU, cost centre and owner, kept in the governance environment. The naming convention already carries region and BU.
  2. Choose how each environment is funded. Use a prepaid allocation for predictable workloads and a pay-as-you-go billing policy for variable ones. Create one billing policy per cost owner per region, and tag its Azure subscription with the cost centre.
  3. Allocate Copilot Credits per environment and switch off "Draw from the available capacity in my tenant" so each environment's prepaid spend stops at its allocation. Enforce it at scale with the environment-group rule Cost controls – Draw from tenant credit pool.
  4. Set the tenant's add-on capacity assignment setting to "Only specific admins". If environment admins are allowed, they can allocate credits to every environment in the tenant, not just their own.
  5. Land the data monthly in the governance lakehouse (sheet 06): Azure cost exports, the Copilot Studio consumption report, licence reports and inventory.
  6. Publish the statement per region, BU and cost centre. Review it at the FinOps board and settle disputes before the books close.
Watch out for

Common traps

  • An allocation alone isn't a boundary. If the environment can still draw from the tenant pool or has a billing policy, it keeps spending.
  • Azure budgets alert but don't stop usage. Where a workload needs a hard stop, add an agent monthly limit with Stop usage, with a margin: it isn't applied instantly and doesn't stop the agent flows the agent calls.
  • Prepaid credits are shared with Microsoft 365. Credits allocated to Power Platform environments reduce what Copilot Cowork and Work IQ can use. Agree the split with the Microsoft 365 admin.
  • Reports lag. Copilot Studio consumption data is aggregated daily and can be delayed, and Azure costs take up to 24 hours. Close the month from exported data, not dashboards.

How do we let finance makers use SAP and sales makers use Salesforce, without opening either connector to everyone?

Steps

  1. Define connector packs: a baseline every maker gets, plus add-on packs per business need, such as finance (SAP, SQL), sales (Salesforce) and engineering.
  2. Create one environment group per pack per region (for example EG-A-FIN-{R}). Give each an advanced connector policy equal to the baseline plus its pack. Use the Power Platform API to copy the baseline policy between groups so they stay in step.
  3. Restrict risky connectors by action. Set them to SomeAllowed and list only the permitted actions, such as read-only Salesforce or named SAP calls.
  4. Bind each environment to an Entra security group and give its members the maker role through a Dataverse group team.
  5. Publish an access package per pack in Entra ID Governance. Require approval from the BU champion, set a 180-day expiry and add a quarterly access review.
  6. Start in mixed mode. Watch for blocked attempts, then switch each group to ACP-only once it's stable.
Watch out for

Common traps

  • Everyone in an environment gets all of its connectors. Don't mix audiences in one environment.
  • Policies stick. Each environment has one effective connector policy. If you move an environment out of a group or remove the group rule, the last policy stays in place until you remove it on the environment.
  • Keep these groups managed. On non-managed environments, nonblockable connectors stay nonblockable.
  • New connectors are blocked by default. Publish a request path so makers aren't stuck.
  • Custom, HTTP and MCP: keep the classic data policy for custom and HTTP connectors. MCP servers can only be allowed or blocked whole.

  2. Publish the rule Cost controls – Draw from tenant credit pool = off on Zone G and AI lab groups, and don't link a billing policy to them.

Principles

  • Prefer a tenant setting or group rule over an environment setting. Rules lock the setting so environment admins can't change it.
  • Put controls in code: the Power Platform API and admin SDKs can apply allocations, advanced connector policies and group membership, so every region gets the same baseline.
  • Pair every restrictive control with a request path and an owner who can approve exceptions.
Watch out for

Common traps

  • Managed-only features. Group rules, sharing limits, IP firewall and alerts need managed environments, and managed environments need premium licences for every user (enforced from Feb 2027).
  • Removing a rule doesn't undo it. Environments keep the last applied connector policy until you remove it on each one.
  • Exceptions drift. Review approved exceptions quarterly and give each one an expiry date.

  • One semantic model, with row-level security by region.

Back-charge rules

  • Overage: credits drawn from the tenant pool above an environment's allocation are back-charged at the internal rate the following month.
  • Corrections: errors found after close are fixed by back-charge or credit in the next cycle, never by reopening a closed month.
  • Unowned spend: charged to the platform budget, and the environment goes to quarantine until it has an owner.
  • Disputes: raised by the regional hub in the dispute window, and decided by the FinOps board.

Maturity path

  1. Showback for two or three months, until regions trust the numbers.
  2. Cross-charge direct costs: pay-as-you-go and licences.
  3. Add prepaid credits and Dataverse at agreed internal rates.
  4. Add shared platform cost and back-charges with an allocation key agreed once a year.
